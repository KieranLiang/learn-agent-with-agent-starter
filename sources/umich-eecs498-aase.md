## L01 课程介绍与 AI 编程格局 🟢

- 四波：自动补全（2021–22）→ 聊天（2022–23）→ agentic 工具 → 现在。
- **打字员与策展人**：打字员写每一行、把时间花在“怎么写”、对正确的定义是“我敲对了”；策展人说明意图、判断产出。同一个工程师，时间分配不同。
- 全课的规矩：**“你能解释它，它就是你的。”** AI 是必须用的，不是被容忍的；评分看理解，任何一行都可能被要求解释。
- 一句话描述协作的形状：“我描述结果，模型产出，我来判断。”
- 为什么先用 Aider：Big Three 是显式的，没有界面替你藏起上下文、模型、提示的决定。“Aider 会过时，原则不会。”

## L02 LLM 怎么写代码 🟡 ★

我们 单元 2“LLM 最小集”的最佳蓝本，只讲四件事，全部落到“这对你用 agent 意味着什么”。

- **Token**：模型看到的不是字符也不是词。标本：`getOrderById` 被切成 get / Order / By / Id。Token 既是成本单位，也是注意力单位。同一个函数，啰嗦的写法 35 个 token，简洁的 9 个。
- **上下文窗口，“唯一重要的资源”**：窗口里有文件、历史、仓库地图、系统提示；**窗口外什么都没有**，没有数据库、没有联网。大上下文的三个代价：成本、延迟、质量下降。标本表：token 翻倍，两两比较的工作量变四倍。
- 上下文漂移：五十轮之后，窗口里大部分是死重，模型分不清哪些现在还成立。
- **幻觉不是故障，是设计**：自回归采样，没有核对事实这一步。标本：训练数据里 `import requests` 比 `import httpx` 多一百倍，你的项目用 httpx 但提示里没提，模型就写 requests。“不是编造，是把一个真实的库用在了错的项目里。”
- 对策一句话：**“模型需要一个事实的时候，把事实给它看。”** 管理上下文最深的理由是准确，不是成本。
- **能力与知识是两条轴**：能力（推理、跨文件、同时守住多个约束）随模型大小涨；知识（读过什么、多新）随训练数据走。混淆两者就会选错模型。
- 出错时按顺序问三个问题：上下文给够了吗；它是不是编了一个 API；任务是不是太难或太新。

## L03 Big Three：上下文、模型、提示 🟢 ★★

- 每次 AI 编程会话都有三个杠杆：**上下文**（模型现在看得到什么）、**模型**（哪个，能力加知识）、**提示**（意图表达得多清楚）。
- 靶心图和三种“差一点”：有模型有提示没上下文（对一个它从没读过的文件做出干净又自信的修改）；有上下文有提示模型不够（半路丢线）；有上下文有模型但提示含糊（做出一个合理但你没要的东西）。**“三中二不够。”**
- **诊断顺序**：AI 错了，先问上下文、再问模型、最后问提示。“多数学生怪模型。通常是上下文。”
- “外科手术式的上下文”三问：这个任务要改哪些文件；改之前必须读懂哪些；哪些只是背景。**“上下文是设计，不是准备工作。”** 全加进去比只加对的更糟。
- 两个最常见的坑：缺上下文（没加进来的文件改不了，结果是一个看起来完成了的半截改动）；历史串味（任务 B 继承了任务 A 的假设，要清空）。
- 选模型看任务，不看偏好：一行的 bug 修复用便宜快的；三个互相依赖的新文件用最强的。
- 反直觉的教学建议：**从会失败的模型开始**。“一个替你兜住错误的模型，会把你需要看见的错误藏起来。”
- 提示：说“做什么”，不说“怎么做”，但“做什么”要具体到接口为止。
- 标本：现场演示。只给 `main.py`，模型去重写一个它没读过的文件；加上那个文件，同样的模型同样的提示就对了。“同一个模型，同一句提示，多一个文件。”
- 带回家的三问可直接当“判”题：50 个文件的项目要改认证，你怎么加文件；为什么把所有文件都加进去结果更差；中途换模型，什么变了。

## L04 Spec 驱动开发 🟢 ★★

- **信息密集关键词**：动词成对出现并且有区别——CREATE 与 ADD、UPDATE 与 REPLACE、DELETE 与 REMOVE、MOVE 与 MIRROR。句式是“动作 位置：细节”。
- 为什么有效：含糊的提示让采样分布很宽，模型就选训练数据里最常见的写法；精确的提示把分布收窄。“有效是因为机制，不是因为模型更懂英语。”
- 提示三档：高（“让它更好”）、中（甜点区）、低（“第 47 行把 X 换成 Y”，那你就成了打字员）。甜点区随模型移动。
- **瓶颈转移了**：2024 年的问题是“AI 能理解我要什么吗”，2026 年是“**我**能说清我要什么吗”。产出质量被计划质量封顶。
- 不对称：人类承包商拿到含糊的需求会来问你，LLM 不问，它猜。所以含糊在这里更贵。**“Spec 就是提示。”**
- 何时写 spec：三个以上文件要协调、步骤互相依赖、要可重复、从零构建。单个 bug 修复不用。经验法则：你会给人类承包商写设计文档的时候，就写 spec。
- **Spec 五段**：高层目标（一句话的为什么）、中层目标（3–5 个可独立验证的结果）、实现说明（依赖、规范、约束——“模型不许猜的东西”）、上下文（起始文件和结束文件，最常被跳过也最重要）、有序的低层任务。
- Architect 模式：一个角色出计划，一个角色改代码。计划出来先停，**读它**，这时磁盘上还什么都没有，是最便宜的纠错点。
- 评分时最常见的四个错：中层目标含糊；缺上下文段；任务顺序错；在任务里直接写代码而不是写指令。
- 带回家的问题：为什么把“每个函数都要注释”写进 spec 而不是指望它——“没写下来的规范，模型从来就没有。”

## L05 现代 agentic CLI 🟢 ★

- Aider 的六步循环：组装 → 回答 → 解析 → 应用 → 修复（失败才有）→ 提交。
- **一把尺子：“下一步动作由谁选？”** 这个问题三年后工具全换了名字也还能用。
- **自主梯度五级**。你在第 3 级时：交出去的是一个有边界的修改任务，你选文件和任务终点，它自动做匹配、修复、测试、提交。
- 取舍：越高的级别花得越多、问你越少。**“本事在于挑对级别。”** 能指着说出是哪个文件的两行修复，用第 3 级更便宜更安全。
- “agentic”四要素：循环、工具、规划、记忆。出人意料的是 Aider 四样都有。**区别在于谁来选。** 把“选下一步”从 harness 移给模型，不需要任何新的模型能力。
- harness 仍然决定的事：**模型只能从一张不是它写的菜单里选**；权限才是真正的安全层；循环需要一个停下来的理由。
- 全课反复出现的设计规则：**“文字是请求，代码和权限才是强制。”**
- 出错时看轨迹：哪一步选错了文件、误读了哪个结果、缺了哪个工具于是它自己凑合。“找出错的那个决定，不是找罪魁。”

## L06 从结对编程到 agent 编排 🟢 ★★

- **谁理解代码**：模型写大部分代码行，你拥有决定和结果。理解要在“合适的距离”：太近是逐行读它写的每一行；太远是接受你没检查过的东西；合适是检查契约和证据。
- 你脑子里要装的四样：设计和理由、做到哪儿了、什么是真的验证过的、什么只是模型声称的。**模型在两次会话之间一样都不记得。**
- **参照点**：给项目状态起短名字（比如 `F6` 代表“预览和应用修改”这个功能）。用名字下指令，也要求模型用名字汇报：“这次改动交付了哪条验收标准、你跑了什么、什么没验证？”
- **从编辑块到工具调用，一步步长出来**（非常好的讲法，可改编成 单元 3 的主线）：
  1. 程序本来只认一种“命令”：模型输出的搜索替换块。
  2. 卡点：模型说“我得看 main.py 才知道”，你手动加文件再说“再看看”。你只是在传话。
  3. 那就给它一个 READ 命令。再给一个 RUN 命令。
  4. 三个命令抽象成同一个形状：**一个名字加一组参数**。这就是函数调用。
  5. 每次“继续”都是人在按。把人自动化掉，就是六行的循环。
- **“模型从不运行任何东西。它只是请求。”**
- 循环前后只变了一件事：下一步由模型选。模型仍然只产出文字，你的代码仍然执行每个动作。
- 循环还缺什么：迭代和 token 上限、重复调用检测、能中途打断、跑命令前的审批。“撤销能管文件，管不了 shell。”

## L07 一次调用的内部：消息、流、工具调用 🟡

- 整个接口就是一个 HTTP POST 和一个 JSON 对象。**“没有会话字段。没有地方放记忆。”**
- 回复结束有三种原因：`stop`（模型自己结束）、`length`（被截断，绝不能当成修改）、`tool_calls`（它在请求你做事）。
- 实测：三个工具的定义让每次请求多 400 token，之后每一轮都带着。
- 工具调用的四个部分：名字和描述（给模型看，用来选）、参数契约（你的代码，检查它要的东西）、分发、结果。
- **标本：一次真实的九步运行**。小模型被要求给 `taskr add` 加一个优先级参数。它读对了三个文件、按依赖顺序写了三个文件，然后在第 8 步执行 `rm -f ~/.taskr.json`——用户真实的任务数据，git 从来不知道这个文件。上下文九步涨了七倍，而且它始终没说自己做完了。
- 复盘方式：没有东西挡在 `rm -f` 和主目录之间（→ 代码里的审批）；没有东西识别“完成”（→ 六个有名字的停止条件）。

## L09 停止条件与审批层 🟢 ★★

**第一部分：一次运行为什么结束**

- “完成”的三种信号：没有工具调用（免费，但沉默不等于完成）、专门的 finish 工具（有意的完成）、验证（声称之后再检查）。
- 标本：同一个任务跑四次，四次都说 done，实际结果各不相同；其中一次的“测试”什么都没运行。
- **六个停止条件**：任务完成、步数上限、token 预算、墙上时钟、重复的相同调用、连续工具错误。每个各抓一类问题。
- **“因为撞上限而结束的运行，并没有完成。”** 日志必须写明是哪一个条件触发的。
- 检查放在三个位置：发请求之前（步数、预算、时钟）、收到回复之后（完成、截断）、执行调用之前和之后（重复、错误）。

**第二部分：动作前面的检查**

- **“停止条件结束运行，但不评判动作。”**
- 撤销能回退什么：写仓库里的文件可以；`rm -f ~/.taskr.json` 不行（从没被跟踪）；`git reset --hard` 不行（git 本身就是那张安全网）。
- 类型化的动作 `add_task(title, due)`，名字就是效果；`run_command(command)`，**参数本身是一段程序**。
- 审批的四个决定：给人看什么（完整的调用，写文件要看 diff）、拒绝之后返回什么（一条带理由的工具消息——“拒绝是一个答案，不是一个错误”）、读操作要不要问、等待时间算不算进时钟。
- **“批准的是命令，绝不是解释。”** 模型给的理由（“清理测试状态”）和命令是同一个模型写的。
- 看着无害、运行有副作用的命令；指向文件的命令（`pytest` 会执行仓库里每个 `conftest.py`，如果上一步刚写了它，批准 pytest 就是批准那个文件）。“你批准的是某个状态下的命令。”
- **审批疲劳**：到第 30 步，提示只是一次按键，不再是一个决定。

## L10 Skills 与大象-金鱼模型 🟢 ★★

- 技能的定义：agent 在任务需要时加载的一个文件夹。“**描述**决定何时，正文决定怎么做。”
- **指令可以住的四个地方**：系统提示或 AGENTS.md（每次请求都在）、工具定义（每次都在，以 schema 形式）、技能（任务需要时）、……。技能与工具的区别：工具是函数，由 harness 执行，完整 schema 一直在；技能是说明，由模型遵照，平时只有描述在。
- 实测“什么都知道”的代价：五个技能的描述合计约 900 token，五个完整正文约 18,000 token。
- **大象-金鱼模型**（Dave Rensin，Google）：
  - 论点：**“设计是新的代码。”** 模型写了大部分代码之后，人能担保的产物是设计文档。
  - **大象**：长的、上下文丰富的会话，记得你和它争过的每一件事。规则：文档通过之前不写代码；先采访再提议；模型先起草你来反驳；只出一份文档。
  - 设计文档四段：问题（三到五句大白话，说不了这么短就是还没想明白）、技术方案、被否决的备选、……。
  - **金鱼**：一个全新的、没有记忆的会话，只知道纸面上写的东西。**“喂大象，用金鱼检验。”** 如果一个新会话没法只靠文档理解、批评、实现它，说明文档靠的是聊天一关就消失的上下文。
  - 三个金鱼评审并行：理解（复述）、批评（找缺口）、就绪（我能照着做出来吗）。
- 这门课自己的设计文档就这样过了六轮金鱼评审。
- 一句带走：“金鱼就是一个几乎空白的上下文。”

## L11 护栏：错误、重试与审批关卡 🟢

- **护栏是你代码里的一个检查，模型没法靠嘴说过去。**
- 先分类再处理失败。标本：把 Codex 指向一个永远返回 502 的端点，它重试 30 次后退出。
- **“超时不等于没做。”** 命令在 30 秒被杀掉时，那条任务存进去了吗？harness 没法知道。重试可能产生两条。
- 批准一个修改，你看得到 diff，git 能放回去；批准一条命令，你看到的是“运行什么”，不是“它会碰什么”。
- **为什么要自动审批关卡**：Claude Code 的权限提示有 93% 被批准。一个几乎总是 yes 的提示就不再是决定了。
- 三种能替人回答的东西：代码里的规则、审查模型、类型化分类器。顺序是代码先、模型其次、人最后。
- 关卡不能承诺什么（“要测量，不能信任”）：Anthropic 公布的自动模式数据里，安全动作被误拦 0.4%，过度的动作放过 17%。

## L13 浏览器扩展与能发短信的助手 🟢

- 浏览器扩展用的是你已登录的浏览器，够得着你登录的每个站点。
- **会话在哪里结束**：harness 只在你的会话开着的时候存在，而你想要帮助的多数时刻它没开着。
- 常驻助手要补的几块：能被程序驱动（不靠键盘）、一台一直开着的机器、一个通道（能发起一轮对话的 MCP 服务器）、触发器（包括定时“心跳”，多数时候什么都没发现就保持安静）、持久记忆。
- 安全：谁能给它发消息，谁就能给模型下指令，所以通道要有发件人白名单。
- 收尾：“harness 一直没变。扩展和通道只是新的进出口。”

## L14 Subagents 🟢 ★

- 从一场你经历过的长设计对话讲起：模型看到的是一摞消息，每次请求都全部重发。
- 子 agent 的定义：**第二个对话**——一份全新的消息列表、自己的工具、一份任务简报、只把报告带回来。
- 跟踪一次真实的委派：模型写的那份简报长什么样；子 agent 的第一条请求里有什么；报告怎么回到主对话。
- **全新的还是分叉的**：全新的只有简报；分叉的带着整段对话。大象是长会话，金鱼就是一个全新的子 agent。
- 两个 harness 都告诉模型要克制地生成子 agent。
- 并行搜索是安全的，并行编辑不是，所以每个子 agent 一个 worktree。
- 子 agent、团队、交接三者对比。

## L15 压缩与提示缓存 🟢

- 满窗的四种处理：报错停止、丢最老的、……、压缩。
- 摘要保留什么、丢掉什么：压缩之前模型知道确切的行，之后只知道“改过那个文件”。
- **压缩就是一次交接**，和子 agent 把报告交回主对话是同一回事。
- 缓存：匹配必须从头精确一致，所以把变化最少的放最前（工具、系统提示），新内容只往末尾加。什么会重置缓存：改一个工具定义就全没了。写缓存比普通输入贵四分之一，读便宜得多。

## L16 Agent 记忆 🟢 ★

- 开场：周一你纠正了模型（“只跑快速测试”），周二它又忘了。
- 记忆 = 模型写给以后的笔记。harness 需要两样东西：系统提示里关于记忆的说明，和写文件的工具。
- 笔记的结构：顶上一行用来以后找到它，然后是内容。四类笔记（关于你是谁、你的纠正、项目、外部资料）。
- 何时写、何时改；关于你的笔记和关于项目的笔记住在不同地方。
- 加载分三级，和技能一样：索引每次都在，单条笔记按需读，更老的靠搜索。
- **一条变坏的笔记**：九月存了跑测试的命令，十月命令变了，笔记还在。
- 事实和方法要分开看：谁写的、是什么类型的东西。

## L17 知识库 🟢

- 问题：每次回答都从零重建。
- 模型维护的 wiki：三层结构，三个操作（加一个来源、问一个问题、像跑 linter 一样检查 wiki）。
- **检索还是编译**：从原始文档里临时检索（RAG），还是事先编译成 wiki 页面。向量检索的局限。
- 模型写了大部分页面之后，读者需要知道该信到什么程度：出处和新鲜度。

## L18 多模型，一个 harness 🟡

- 一种内部格式，每个提供方一个适配器，在边缘翻译。
- 一次会话里其实有很多份工作（主循环、压缩、子 agent、起标题……），可以各用不同的模型。规划者加编辑者。推理强度是一个旋钮。
- 谁来选模型：四种答案，多数 harness 混用。

## L19 在自己机器上跑 Claude Code 项目 🟢

- 课程组自己的工作方式：一个终端会话的局限 → 多个终端会话 → 协调者加多个线程，从手机发消息。
- 一个线程听谁的：它从很多地方收到文本，必须分清哪些文本算指令。
- 什么能比线程活得久：被纠正过的事变成写下来的规则。

## L20 手绘课件与视频是怎么做出来的 🟢 ★（2026-11-25 补读课件文字）

- **核心问题与检查原则**：本讲是对课程自身工具链的案例研究（case study），包括绘图应用 Excalidraw、画布服务器（canvas server，`mcp-excalidraw-server`）和渲染工具 `excalive`（小节“How Our Hand-Drawn Lectures Are Built”）。全讲围绕一个问题：“when the work is a picture or a voice, something you look at or listen to, how does an agent check it?”（小节“The running example”）。贯穿始终的答案是：agent 必须检查“真实输出”而非预览（“when an agent checks its work by looking, it has to look at the real output, not a preview of it”）（小节“A contact sheet of stills”），并且把图片或声音翻译成模型能读的形式，再留给人做最终把关（“when the output is a picture or a sound, the agent needs a translation of it into something it can read, and a person still has the final listen”）（小节“Checking a voice nobody has heard”）。
- **场景即 JSON 与 CLI/MCP 取舍**：Excalidraw 的场景文件（scene file）是纯文本 JSON，含元素 `id`、宽高 `sixteen hundred` × `nine hundred` 页面上的数字坐标 `x`/`y`、控制线条手绘抖动的粗糙度（roughness，课程图画用 `1`、列表标记和表格线用 `0`）和固定随机抖动的随机种子（seed）（小节“A scene as JSON”、“Where the wobble comes from”）。画布服务器支持 CLI、MCP（共 `twenty-six` 个工具）和 HTTP 三种入口，课程 harness 选用 CLI，因为无需在各 harness 分别配置，且用 MCP 时“twenty-six tool definitions would sit in every request whether the session draws anything or not”（对照 L10 技能与工具的上下文成本）；多 agent 共用端口会互相清空画布，需各占独立端口（小节“One canvas with three ways in”）。
- **看图闭环与“真实输出”踩坑**：模型写 JSON 并通过画布服务器的 `screenshot` 拿到 PNG 回传下一次请求自检，底层通过 `jsdom` 做无头渲染（headless rendering）实现无人值守生成，并由绘图技能自带 Nunito 字体文件（小节“How an agent checks its own drawing”、“Drawing without a browser”）。真实事故：画布截图把居中标签（centered label）坐标当左边缘，导致首批视频里“every centered label in thirteen of the fourteen diagrams was shifted right by half its width”，而所有静态检查全过；后来改让 agent 看 `excalive` 导出 PDF 用的真实渲染静帧拼成的联系表（contact sheet，每页 `twenty` 个点击步）才发现（小节“A contact sheet of stills”、“What the checks miss”）。
- **单一数据源与无渲染机械检查**：早期视频曾单独写约 `nine` 分钟的摘要稿，结果对 `eighty` 分钟的课而言像预告片且与幻灯片脱节；后来统一只写一份故事文件（story file），同时生成幻灯片、讲者排练稿（按每分钟约 `hundred and fifty` 词重写，因原讲义只有讲者实际语量的三分之一到四分之一）和视频旁白（本地开源模型 Kokoro 合成，用词典 lexicon 把 `K2.5` 写成 `"K two point five"`）（小节“Narration taken from the notes”、“A voice on your own machine”）。渲染前用约 `1` 秒跑四项机械检查（第一项不过不准渲染）：① 画面每行字都在讲义里被念到；② 用真实字体量宽度防越界（如起点加实测宽度超过 `fourteen hundred and eighty`）；③ 筛查语音易错词（缩写日期、带字母的百万数字、四位数被念成年份、星期、“the next slide”及 `twenty-five` 秒内重复句）；④ 口播数量与画面元素数一致（小节“A scene as JSON”、“Checks before any render”）。
- **盲听检查四道漏斗与残余盲区**：agent 听不见音频，于是依次跑四道检查：① 用音素转换器（phonemizer）看疑难词重音；② 用语音转文字模型 Whisper 转录并与脚本做 diff（必须用大模型，小模型曾把 `"everything"` 听成 `"nothing"`，且能抓出 `"a round"` 融成 `"around"`）；③ 让没见过课件的全新模型（fresh model）模拟无法回放的听众挑出听不懂的段落；④ 真人戴耳机试听（小节“Checking a voice nobody has heard”）。机械检查仍会漏掉三件事：标签压在箭头上、居中文字偏右、人名重音怪异（Whisper 仍会写对拼写）；因此检查不能把人工降至零，而是把人工压缩到只看联系表和抽听标记片段（小节“What the checks miss”）。
- **自带命令的技能与“一次一讲”批产**：`excalive` 第一天就从 Claude Code 插件改成普通技能（plain skill）文件夹：`SKILL.md` + `bin/`（把命令和脚本直接随技能打包，更新时指令与工具不会脱节，且兼容 Claude Code、Codex、Cursor）+ `references/`（存放风格指南 house style，仅在画图写稿时读取，体现 L10 三级加载）（小节“A skill that carries its command”）。`three` 天重做 `eighteen` 份课件时采用“一次一个 agent 负责一份课件”：指南写入全部坐标与规则，禁止抄前一份课件以防复制偶然错误；每个 agent 把指南缺口记入笔记文件，跑完再修指南，绝不中途改指南（此前曾有 `two` 个早期 agent 因中途改指南而重做）；各用独立端口并按文件名提交，最后由人审阅联系表（小节“From podcasts to videos”、“Agents one deck at a time”）。
- **对我们**：最直接用于 **单元 12（可靠性与评估）** 和 **单元 16（给 agent 搭环境）**——可拿“无法跑测试的图/音怎么检查”、4 项无渲染机械检查、盲听四步漏斗以及“居中标签在 14 张图错 13 张”的真实事故，讲透“把主观判断转成机械检查”“检查真实输出而非预览”以及“人工把关不会被消零但可被压缩”；**单元 7（记忆与 Skills）** 可直接用 `excalive` 把 `bin/` 打包进技能、三级加载 `references/`，以及“CLI 省掉 26 个 MCP 工具定义进每次请求”的取舍；**单元 9（多 agent）** 和 **单元 21（放手与把关）** 可借用多 agent 共享端口踩坑、不中途改规范、逐份交接等经验。

## 给我们教学法的借鉴

- **固定的一讲结构**：回顾上一讲留下的问题 → 一个框架 → 现场标本 → 5 分钟讨论题 → 三个带回家的问题。我们的“一组”可以照这个节奏。
- **让失败看得见**：用弱模型、给少的上下文，让学生亲眼看到错，再只改一个变量让它对。
- **一句话能带走**：每讲都有一两句加粗的断言（“三中二不够”“文字是请求，代码才是强制”“批准命令，不批准解释”）。
- **从学生已经会的东西长出新概念**：工具调用是从“编辑块”一步步长出来的，没有凭空定义。
