## 第 2 讲 从用户视角看 agent（一）：Claude Code 怎么工作 🟢 ★★

可以几乎原样改成我们 单元 3 的开头。

- 开场问题：“你在 Claude Code 里敲下一句话之后发生了什么？”
- **Agentic loop**：一次用户输入 = 很多次模型调用加很多次工具执行。三步循环：收集上下文 → 生成动作 → 运行工具。
- **你还没打字，上下文就已经有 1 万多 token**：系统指令、项目环境、记忆（CLAUDE.md）、工具定义、技能和 MCP 的名字与描述。
- **它不会把整个仓库发出去**：仓库留在磁盘上，模型按需用 grep 拉一小片进上下文。
- **模型提议，harness 执行**：模型发出 `Bash("pytest")` 这个请求；harness 解析、查权限、执行；结果回到模型的上下文。
- 权限层夹在意图和执行之间：手动、自动接受编辑、绕过、自动（小模型审查）。
- 上下文会增长，然后被压缩；压缩后会重新注入 CLAUDE.md 和记忆。
- **记忆**：agent 在两次运行之间是无状态的；所谓记忆就是会话启动时加载的文件。“每创建一条记忆，都是在决定什么东西要被永远重读。”
  - 没有记忆的四种症状：重复交代、丢失决策理由、重复探索、行为不一致。“记忆让指令变成惯例。”
  - CLAUDE.md（人写，规则和指令）对比 auto memory（Claude 写，学到的东西）。加载顺序从组织到用户到项目到本地。
  - **CLAUDE.md 里该放什么**：命令（怎么跑测试）、硬约束（绝不提交到 main）、agent 没法便宜地推断出来的事实。**不该放**：模型本来就知道的、linter 已经管的风格、长篇大论、秘密。单文件 200 行以内。
  - 金句：**“上下文是租的，记忆是自己的。”** “过期的记忆比没有更糟，它会主动误导。” “像对待代码一样对待记忆：评审、修剪、纳入版本控制。”
- **四种扩展机制，解决四个不同问题**：skill（agent 该怎么做一件事）、MCP（它够得着哪些外部数据和动作）、hook（生命周期事件上自动发生什么）、plugin（怎么打包分发）。四者在循环里挂在不同位置。
- **标本：设计练习**。把 7 个需求归类并说明为什么别的不合适：应用公司 API 规范（skill）、读 Jira 工单（MCP）、每次编辑后格式化（hook）、引导多步部署（skill）、完成后发通知（hook 加 MCP）、禁止写生产（hook 或策略）、跨仓库共享（plugin）。可直接当“判”题。
- MCP 安全四条：最小权限、读写分离、**不信任工具返回的内容**、安装前审查。

## 第 3 讲 从用户视角看 agent（二）：多 agent 与最佳实践 🟢

- 案例 Superpowers：**同一个模型、同样的工具，只是指令不同**，流程就从“直接开写、靠迭代修”变成“澄清问题 → 批准设计 → 写详细计划 → 测试驱动构建 → 评审验证 → 收尾”。
  - 关键设计：光装技能不够，装了不代表 agent 会去看。用一个 SessionStart hook 把“引导技能”注入上下文，保证每次会话、清空和压缩之后都生效。
- 案例 Caveman：双向压缩 token。技能改变模型怎么写，本地代理改变模型读到什么。786 行测试输出变成一句“3 个测试失败：client.ts:88 超时”。原文保留可取回。
- **三条扩展轴**：并行 agent（买吞吐，不买质量）、子 agent（买吞吐和专注，父 agent 看不到中间的乱七八糟）、长时间运行（买范围）。
- 手动并行靠 git worktree。到 20 个会话就撑不住：计划在你脑子里，会话互相看不见，分支要你合，过程不可重复。
- 子 agent：独立的上下文窗口、工具和权限。**何时留在主对话**：来回迭代、各阶段共享上下文、小改动、在意延迟。**何时委派**：输出冗长且不再用、需要限制工具或权限、自包含并只需返回摘要、可并行。
- 子 agent 与 agent team：前者只向调用者汇报；后者有共享任务列表，队友之间直接通信，成本更高，只在工作需要讨论时用。
- 长时间运行的两种方式：`/goal` 给一个**可验证**的终止状态（“所有集成测试通过”可以，“重构代码”不行）；`/loop` 按间隔重跑，直到你喊停。
- **Programming 3.0**（讲师自己的提法）：1.0 写机器指令 → 2.0 写编程语言 → 3.0 表达目标。越往后不确定性越大、生产力越高。**不确定性是核心主题**，来源有四层：自然语言的歧义、检索和上下文的漂移、模型生成的随机性、工具循环和环境的非确定性。
- 最佳实践三组：定义（先说清假设；给结果、不变量、约束和验收测试）、控制（提议和执行分开；显式管理上下文）、验证（便宜而频繁的检查胜过最后一次昂贵的评审）。
- 金句：**“别指望 agent 是确定的；要让它周围的系统可靠。”** “自主权要和风险匹配。”
- 委派阶梯五级：聊天机器人 → 助手 → agent（委派一整块工作）→ 多 agent → 系统化的工作流。

## 第 4 讲 Agent 设计（一）：上下文管理与工具设计 🟢 ★★

- ReAct 三态对比：只推理（没人检查，小错累积成自信的幻觉）、只行动（没计划，原地重复）、两者交替。
- Agent 循环的 20 行伪代码。**harness 设计者要做的四件事**：写工具定义；组装上下文；校验请求、查权限并执行；处理结果并管理上下文。
- 三大组件共用一个上下文窗口：模型加循环、工具加护栏、状态（上下文加记忆）。
- **agent 怎么找代码**，四种方式对比表：glob 和 grep（名字可猜时最好，代价是多花轮次）、语义索引（措辞对不上代码时）、外部信号（堆栈、失败的测试、git 历史，精度最高但不是总有）、语言服务器（改动要跟着引用走时）。实践：先 grep，名字用完了再上索引。
- **agent 怎么改代码**，四种方式：整文件重写、统一 diff、搜索替换、结构化（AST）编辑。各有各的失败方式。
- Shell 是最强也最危险的工具。要考虑：隔离、失败信号、输出量、时长、预算。
- **工具设计五条**：少而正交；专用优于通用（`search_orders(customer_id)` 胜过裸的 `run_sql`）；输出省 token（**工具设计就是上下文设计**）；报错要能教人（给修复提示）；默认幂等。
- 术语演变：提示工程（怎么指示模型）→ 上下文工程（模型该看到什么）→ harness 工程（agent 该怎么运转）→ 目标工程（什么算成功）。讲师声明他不一定喜欢这些词。
- 提示技巧 8 种，每种配“何时用、何时换下一种”：零样本、少样本、角色、思维链、思维树、自洽投票、提示链、元提示。讲师提醒：其中一些已经过时。
- **上下文是有限资源**，三个代价：成本（每步重发整个窗口）、延迟、注意力（越满越容易漏掉中间）。
- 上下文窗口解剖（示意）：系统提示约 2K、工具定义约 6K、项目环境约 8K、检索内容约 25K、消息历史约 80K 且还在涨。
- **管理上下文的四级手段，从无损到有损**：准入（在门口整形：4.8 万 token 的原始网页变成 900 的摘录）→ 外置（需要时才加载：60 个工具 schema 变成索引加 3 个）→ 变换（去重、遮蔽旧观察、滑窗）→ 压缩（LLM 摘要，最后手段）。
- **上下文的五种失败**：中毒（幻觉进了窗口后来被当事实引用）、分心（历史太长，开始模仿自己过去的动作）、混淆（无关工具和文档带偏）、冲突（新旧信息矛盾都留着）、漂移（真目标被埋，换成了邻近的子目标）。
- **Agent = 模型 × harness**。模型定上限，harness 定实际表现。数据：同一模型换 harness，SWE-bench Verified 从 43/169 到 72/169。

## 第 5 讲 Agent 设计（二）：多 agent 系统 🟢

- 拆分的四个理由：专门化、隔离（不同权限）、并行、上下文管理。
- 每种架构背后的**三张图**：控制图（谁协调）、任务图（怎么分解）、通信图（怎么沟通）。
- 八种架构一张表：主管-工人、层级、流水线、黑板、委员会、市场、蜂群、动态拓扑。各自的最佳场景和弱点。
- 任务分解的六个维度：按数据、专长、阶段、假设、工具、权限。
- **好的子任务包含什么**：目标、输出格式、输入和上下文、完成测试、边界和排除项、预算和期限、可用工具和权限、依赖。标本：“研究存储系统”对比写清楚的版本。
- 粒度取舍：并行只有在省下的串行时间大于规划、沟通、合并成本时才划算。
- 分解失败六种：重叠、缺口、隐藏依赖、输出合并不了、丢失全局上下文、拖后腿的那一个。
- 沟通：自然语言承载内容，结构化协议承载协调（DELEGATE、REPORT、CANCEL 这类操作让运行时不用问 LLM 就能路由和重试）。
- **多 agent 继承了分布式系统的全部难题**：超时之后对方到底执行了没有；慢和死分不清。再加上黑盒 LLM 的问题：摘要丢信息、过期信息、信念冲突、没人认领、循环提问。
- MCP 与 A2A：前者是 agent 到服务（一次工具调用），后者是 agent 到 agent（长时间任务）。
- 设计原则第一条：**真的需要多 agent 吗？**

## 第 6 讲 Agent 设计（三）：记忆与可靠性 🟢 ★★

- 记忆设计七问：值得留吗、变成什么形式、放哪儿、这个任务需要它吗、能推出什么更一般的结论、还有效吗、谁拥有它。
- 何时用记忆的三种控制方式：每轮自动、运行时按规则、模型自己决定。
- **遗忘是一等操作**：标记失效、彻底删除、到期、分层淘汰。记忆要带**生效时间和出处**。
- 记忆失败八种：检索不到、污染上下文、把推断存成事实、过期、越界到别的用户、以偏概全、持久化的提示注入、无限增长。
- **可靠性的算术**：每步 95% 成功，50 步全对的概率只有约 8%（13 次里 1 次）。
- **故障从哪一层来，五层各一张表**（失败、agent 做了什么、怎么修）。这五张表是六门课里最实用的材料之一：
  - 任务说明：目标含糊（“修登录 bug”修错了一个）、代理目标（“让测试通过”结果删了测试）、没说的约束、没有完成定义（永远在重构）、目标冲突。
  - Harness：截断丢了规则、把过期笔记当事实、半截编辑、没设步数上限、等一个慢的子 agent。
  - 模型：幻觉出不存在的函数、违反指令、推理错误、说的和做的不一致、没验证就宣布成功、长程退化（撤销了自己第 12 步的修复）。
  - 工具：输出被截断、静默失败（退出码 0 但结果为空）、schema 含糊、偶发超时、误导性报错。
  - 环境：缓存过期、版本不对、随机失败、页面改版、限流。
- 为失败而设计，五句话：把“完成”写成测试；给每次运行设上限；要证据；失败要响亮；环境要钉住并隔离。

## 第 7 讲 Agent 设计（四）：评估 🟢

- 组件级评估（规划、记忆、工具使用）与端到端评估（成功率、成本、延迟）。
- 评估目标的演变：预测文本 → 给出正确答案 → 给出更受偏好的回答 → 产出能跑的代码 → 完成交互式任务。
- 八个基准逐个讲清“agent 在哪儿操作、典型动作、评什么”：GAIA、BFCL、WebArena、OSWorld、SWE-bench、τ-bench、Terminal-Bench、TheAgentCompany。有一张总表。
- **数据泄漏有四层，不只是训练**：训练泄漏、评估时泄漏（上网搜到答案）、环境泄漏（沙箱里露出未来的提交）、对基准过拟合。所以“模型没在测试集上训练过”远远不够。
- 评估的难处：多数基准只给一条说清楚的指令，而真实工作是含糊的、会被打断和修改的；单轮评分奖励自信的猜测，问澄清问题反而吃亏。
- 基准饱和得很快：SWE-bench Verified 22 个月从 33% 到 95%。
- 实际 agent 要同时看能力、成本、速度三个维度，用帕累托前沿比较。

## 第 8 讲 Agent 设计（五）：省钱的 agent 🟢 + 🟡

- **成本公式**：用户数 × 每用户会话数 × 每会话轮数 × 每轮步数 × 每步 token × 每 token 价格。后四项是可以压的。
- 学生真实使用数据（很好的标本）：主 agent 每步 token 中位数 20 万到 30 万；**97.6% 的 token 是缓存读取**；价格比大约是缓存读 : 输入 : 输出 = 1 : 10 : 50。
- 四个杠杆各有对策：
  - 减少轮数：第 k 轮要重读前 k−1 轮，总成本随轮数平方增长。先规划、结构化分解、交回前自我验证。
  - 减少步数：独立调用批量并行、复用计划和技能、一开始就把要读的读完。
  - 减少每步 token：丢掉过期的、缩小进来的、只加载需要的。输出侧：限定长度和格式、用 schema、按步骤调推理强度。
  - 降单价：稳定前缀吃缓存、能等的走批处理、模型路由（事先选、失败再升级、逐步重选）。
- **每种节省都有反向成本**：压缩之后要重读文件；便宜模型一个坏计划可能多出很多步；子 agent 重复读共享上下文。净节省 = 毛节省 − 反向成本。
- 给每个任务设预算，进展停滞就停。**“到底需不需要 LLM？”** 步骤每次都一样就写脚本。
- 完成时间看关键路径，不是各步之和。并行更快但总 token 更多。
- 三种 harness 架构：单体、模块化、微内核。🟡
- 八个 harness 各自的独特设计（Claude Code、Codex CLI、DeepSeek Harness、OpenCode、Pi、oh-my-pi、OpenClaw、Hermes）。以后讲“harness 之间差在哪”时有用。

## 作业 1 Mads-Lens：观察 agent 工作 🟢 ★

- 任务：用 Claude Code 给 Claude Code 自己做一个网页前端，实时显示轨迹（每个工具调用的输入和结果）、状态、花费、子 agent 的树状结构。
- 对我们有用的部分是**第一步**：`claude -p "<prompt>" --output-format stream-json --verbose` 会一行一个 JSON 事件地打印整个过程（init、assistant、tool_use、tool_result、最后的 result 带花费、时长、轮数）。学生被要求先在终端里读这些事件，再写任何代码。
- 这就是我们“解剖 Claude Code”实践的现成做法：零代码，只读事件流。
- 报告要求三个观察，每个都要落到会话里的具体时刻：agent 怎么工作（哪里花的时间比你预期多、读了什么你不会读的）、一个坑、一条教训。可以直接借来当我们的课后反思格式。

## 作业反馈讲：用 agent 的十个坑 🟢 ★

来自全班真实会话日志的统计，每条都有数据。

| 坑 | 对策 |
|---|---|
| P1 盲信 agent 的说法 | 要证据；亲手查一个案例 |
| P2 搞不清 agent 到底建了什么 | 小步走：读 diff、提交 |
| P3 会话太长，压缩丢了上下文 | 一个任务一个新会话，笔记写进文件 |
| P4 一次叠很多改动 | 一次只改一处，和基线比 |
| P5 并行会话互相踩 | 每个会话一个 worktree 和分支 |
| P6 agent 跑了破坏性命令 | 先提交；禁掉 `rm -rf` 和 reset |
| P7 泄露密钥 | 密钥放环境变量，绝不进 prompt |
| P8 把一次有噪声的运行当结论 | 多跑几次看分布 |
| P9 发泄情绪而不是引导 | 贴报错，让它诊断 |
| P10 平台问题、电脑休眠 | 检查环境；长任务放 tmux |

- 最大的转变：“从让 agent 产出代码，变成说清楚它的工作将如何被验证和信任。”
- 好的迭代循环：从简单基线开始 → 提一个假设 → 改一处 → 测试 → 验证通过就记一个版本 → 重复。
- 数据点：排名第一的学生自己只花了不到一小时。会不会用 agent 是关键。

## 第 12 讲 LLM 推理服务：投机解码 🔴（2026-11-25 补读课件文字）

- **逐 token 解码受限于显存带宽（memory-bound），投机解码（speculative decoding）用草稿并行验证换低延迟且保持输出精确**：在单张 H200（带宽 4.8 TB/s、算力 989 TFLOPS）上运行 Llama-3-8B FP16 时，每生成一个 token 都要重读 16 GB 模型权重，至少耗时 `≥3.3 ms`，每加载 1 字节只做约 1 次浮点运算（FLOP），远低于打满计算核心所需的约 206 次，算力大量闲置（第 5、14 页）。投机解码由小草稿器（drafter）先猜 `k` 个 token，再由目标大模型（target）在一次前向传播（pass）里并行验证，并按拒绝采样（rejection sampling，以 `min(1, p/q)` 概率接受，被拒时从归一化的剩余概率 `max(0, p − q)` 重采样）决定去留，从而使输出分布与原模型完全一致（第 6、9、12、13 页）。加速比满足 `S = E / (ck + 1)`，其中 `E = (1 − α^(k+1)) / (1 − α)` 为每轮期望接受数、`α` 为接受率、`c` 为草稿步成本与目标步成本之比；例如 `α = 0.8, k = 4, c = 0.05` 时 `E ≈ 3.4`、`S ≈ 2.8×`（第 15 页）。
- **七类草稿路线与“便宜比准更重要”的原则**：课件将草稿来源分为七族——独立小模型（T5-small、Llama 3.2 1B）、自投机（self-speculation：LayerSkip、SWIFT）、预测头（prediction heads：Medusa）、特征级草稿器（feature-level drafters：EAGLE 1–4）、原生多 token 预测（native MTP：DeepSeek-V3 MTP）、并行与块草稿器（parallel and block drafters：DFlash、DSpark），以及复制与检索（copying and retrieval：N-gram lookup、SuffixDecoding）（第 22、46 页）。在 T5-XXL（11B）的英德翻译贪心解码（greedy decoding）实验里，T5-small（77M）、T5-base（250M）、T5-large（800M）的接受率 `α` 只从 `0.75` 微升到 `0.80` 和 `0.82`，但草稿成本涨了 10 倍，加速比反而从 `3.4×` 掉到 `2.8×` 和 `1.7×`，说明“一个够便宜且 `α` 尚可的草稿器胜过更准但更慢的草稿器”（第 18 页）；把温度（temperature）从 `T = 0` 提到 `T = 1` 时，由于要匹配整条分布而非单个最高概率 token，三者加速比会进一步降到 `2.6×`、`2.4×` 和 `1.4×`（第 19 页）。
- **检索式投机直接瞄准 agent 的重复负载与 API 计费边界**：agent 任务在代码编辑、SQL 和工具调用中会在多次请求间重复大量文本，SuffixDecoding 在 CPU 上对历史输出（全局）和当前请求维护后缀树（suffix tree），使草稿成本 `c ≈ 0`，在 agent 任务上最高提速 `5.3×`，比 EAGLE-2/3 快 `2.8×`（第 43、44 页）。生产中也常见检索式方案：Cursor 投机编辑（speculative edits）让 70B 模型整文件重写，直接拿原文件当草稿来验证，只对改动片段逐 token 解码，速度达 `13×`、约 `1000 tokens/s`；OpenAI 预测输出（Predicted Outputs）让 API 调用方传入预期输出（常为当前文件）以加速返回，但明确标注“被拒绝的 token 仍会计费”（Rejected tokens are still billed），且全文件大幅重写时接受率低、会退回常规解码（第 45 页）。
- **批处理（batching）、长上下文（long context）与 MoE 下的延迟–吞吐权衡**：在理想 H200 屋顶线模型下，每次读取 16 GB 权重的算力拐点约为 `n = batch × (k + 1) ≈ 206` 个 token，因此“批处理和投机解码争夺的是同一份约 206 个免费槽位：批处理买总吞吐，投机解码买单用户速度，如何切分是服务等级目标（SLO）的选择”（第 14、65 页）。在 `α = 0.8`、不计草稿成本的模型下，batch 16 配 `k = 4` 可在同样 `3.3 ms` 步长内把单用户速度从 `299` 提到 `1,005 tok/s`，但到 batch 256 时 `k = 4` 会把步长拖到 `20.8 ms`，单用户速度降到 `162 tok/s`（总吞吐 `41K`），低于关闭投机（`k = 0`）的 `241 tok/s` 和 `62K`（第 65 页）。长上下文会扭转这一限制：因 KV 缓存（KV cache）按请求私有，8K 上下文、batch 32 时每步需读 `34 GB` KV 缓存而权重仅 `16 GB`，MagicDec 用固定大小的稀疏 KV 缓存起草、完整缓存验证，在 4K token 以上的 batch 32–256 可提速高达 `2.51×`（第 69–71 页）。而在混合专家模型（MoE）上，验证多个草稿会路由到更多专家、大幅增加权重读取，常开投机最高拖慢 `1.5×`，需要由 TurboSpec（最大化有效吞吐 goodput，即生成 token 数 ÷ 步长，轻负载最高降延迟 `3.2×`、峰值自动取 `k = 0`）或 Cascade（按效用动态开关 MoE 投机，把最坏拖慢压到 `5%`）在运行时调 `k`（第 66–68、72–74 页）。
- **对我们**：本讲属于 LLM 推理服务与硬件层系统优化，归入单元 20（推理服务）（因为我们的主线是先用好模型和设计 harness，不涉及 GPU 调度和推理引擎实现）。但其中与 agent 延迟和成本直接相关的工程事实——检索/编辑类任务把原文件或历史输出当草稿提速、OpenAI Predicted Outputs 对被拒草稿照样计费、服务端单用户低延迟与高并发吞吐彼此竞争——可以作为单元 14、20 讨论“能力、成本、速度一起看”时的背景参考。
