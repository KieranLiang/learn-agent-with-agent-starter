## 第 1 讲 欢迎来到未来 🟢 ★★

- 起点问题：作业交给 AI 就能做完，那满分证明了谁的什么能力？作品还在，作品与能力的对应关系变了。
- 大学还能教什么，三个说法：**“信息差、能坐牢、能驾驭。”** 知道世界上有什么、去哪找答案是信息差；做了决定有人担后果是能坐牢；把人、工具和反馈组织起来把事做成是能驾驭。课程最关心最后一项。
- 语言模型：先理解为条件概率 Pr[token | context]。接口简单，但输出会进入后续上下文，所以一个静态的分布能展开成很长的计算。
- Agent：模型加上运行它的程序、工具和环境形成一个反馈循环，承载这个循环的外围系统叫 harness。**“理解 Agent 不能只看模型答题有多聪明，还要看它能观察什么、操作什么，以及操作以后能否知道自己做对了没有。”**
- **先用好，再理解原理**：“我不会，所以不能做”改成“先让工具帮我做出一个能观察、能检查的结果”。但先用好仍然包含验收。
- 限制我们的常常是“还没想到这件事也能委托”。去找一天里那些重复、烦琐、又能判断对错的数字任务。
- 第一次让 agent 探路，之后把成功的操作沉淀成可检查、可修改的脚本，昂贵的探索就成了可复用的资产。
- **标本：二维码 Excel 为什么掉进泥潭**。需求看着很具体，里面仍藏着大量选择（编码、每帧装多少、怎样才算完成）。一个模型花了 6 小时；另一个交了**硬编码版本**——只让当前输入看起来正确。后来靠少量提示调整了计算结构才做对。
- AI slop 的判据不是文件多大、代码多丑，而是**修改有没有局部性**：改一个地方会不会迫使整个系统重来。
- **Intent、Spec、Impl**：意图往往连提出者自己都没想清楚；规格描述行为和约束；实现必须在每个分支上做确定的动作。同一意图允许许多规格，同一规格允许许多实现。模型靠猜来填空。颜色和变量名猜错无所谓，**架构、数据表示、验收标准猜错代价就大**。
- “立即遵循指令”有时会把事做坏：重要选择还没被看见就固化在代码里了。
- **让大工程获得及时反馈**：拆解、验证、迭代，共同缩短“做了一个决定”与“知道决定是否正确”之间的距离。
- 夸张算式：生成能力提高一千倍，哪怕只有 1% 是垃圾，垃圾的绝对量也是旧时代全部产量的十倍。生成越来越快，逐行阅读却没法同样加速。
- 收尾的问题：“为什么我要招你，而不是买一个 200 美元的 Claude Max？”

## 第 2 讲 提示词与上下文工程 🟢 ★★

- **模型看到的远不止你刚输入的一句话**：系统指令、工具说明、AGENTS.md、加载的 skill、代码、文件、历史、工具返回都在上下文里。
- **指令和材料要分开**：工具返回的一段文章是分析对象，并不因此有资格给 agent 下命令。来源、作用范围、优先级都是组织上下文时要考虑的。
- 提示词里的要求和程序里的机制一起决定行为。**“一句‘请遵守规则’，并不等于已经实现了一个可靠的执行边界。”**
- 小实验：让 agent 说明当前任务有哪些目标、工具规则、项目约定、输出要求。但模型的自述不能当成实现机制的完整说明。
- 学习方法：借 AI 弄清一个问题 → 合上资料用自己的话重述 → 让它追问含糊处、找反例 → 用推导或程序结果核对 → 再讲一遍。复述时卡住的地方最能暴露缺口。
- **写清楚“完成”是什么**。标本：“一句话生成极品飞车”和“现代风格的个人主页”——模型没有在任何一步明显违背指令，却在一连串默认选择之后做出了另一个产品。
- 经验法则：**“写清楚你的指令，承担一切‘不明确’的后果。”** 没说明的地方，就是把决定权交给了模型。检查办法：让另一个人只看要求和产物，能否判断任务已完成。完成的语义还包括失败：验证不了就该报告缺什么，而不是交一段肯定的总结。
- 一步有限为什么能完成复杂任务：把输出看成能存放中间状态的**工作纸**。
- **标本：三道刁钻的写作题**（藏头加嵌字的八句诗、十八个同偏旁的字写成一句有故事的话、全同音的文言故事）。形式约束可以逐项检查，文学性不行。还暴露了规格歧义：“同音”包不包括声调？“同偏旁”是字形还是词典部首？很适合当“判”题。
- **上下文里的规则也会争夺注意力**。标本：你说“白色背景，不要半透明”，模型把这句话写进了代码注释。每出一次问题就加一条永久规则，上下文越来越长。更好的做法：长期规则保持简短；任务细节按需加载；**能直接检查的要求落到代码和验证上**。删掉一段无关说明，有时和加一条关键要求一样有效。
- “你是一位审稿人”还不够：角色只给了语气和结构，没给方法。把审稿拆成三条不同路线（从判据出发、审查证据、站到复现者或反方），独立形成意见再比较分歧。**Skill 真正值得保存的是搜索策略、判断标准和检查点。**
- **代码库本身也是提示词**。成熟的大仓库已经做了很多决定，agent 沿着现有结构补充；空项目里每次局部实现都可能顺手做出一个长期设计决定，slop 会叠加。
- 标本：token 花完了研究没推进。可能是反馈太粗（总分没变快，不知道是哪里的问题），也可能把“实现好这个想法”当成了目标，而真正要回答的是“这个想法成不成立”。
- **人该盯哪儿**：按决策影响和返工代价分配注意力，不是平均撒在每一行上。接口看过、结果可检验、出了问题能替换的，放手。会扩散的接口决定、昂贵或难恢复的动作，提前看。
- 探索：多想一会儿和多探索几个方向是两种不同的算力用法。标本：给孩子取名，直接要答案会得到高概率组合（新一代“子涵”）。**探索空间和评价方法要一起设计**，否则只是把一个平庸答案变成一百个。

## 第 3–4 讲 版本管理 🟡（只看了小标题）

- 从“我想撤销”推导出快照；提交要留下可以理解的变化；用原子变更推进项目。
- 开发者可以并行复制之后，困难转移到了协作。“从零开始，你就是包工头。”
- 对我们：日常操作层已经会 Git 命令，这里讲的是底层的为什么。agent 并行需要 worktree 的道理在这里。

## 第 5 讲 软件工程的来龙去脉 🟡

- 软件危机从哪来：程序员贵，懂编程的人不一定懂客户的业务；Intent、Spec、Impl 的差距从一开始就存在。
- 瀑布模型的原文其实在警告照着瀑布做会失败。把阶段图看成**数据依赖图**：设计要消费需求里的信息，测试要有规约作依据，但这并不要求每个阶段只走一次。
- 契约式设计：前置条件（调用者保证什么）、后置条件（实现者保证什么）、不变量。
- “留白也是一种决定”：合法的、非法的、尚未规定的。
- LLM 时代差距移到了哪里：用户没说“支付超时怎么办”，模型为了写完程序会自己选一种，而且每次可能选得不一样。

## 第 6–7 讲 需求和架构 🟡

- 代码便宜以后什么更重要：我们究竟要做什么。
- MVP 帮助发现需求，也会掩盖困难：原型走通了正常路径，容易让人产生“我已经驾驭了 AI”的错觉。
- “几行代码也有架构”：架构决定怎样分解问题、安排职责，让一些事变容易，也决定另一些事将来改起来多贵。
- 标本：教务系统。计算机系改成计算机学院，ID 要不要变？引出事件溯源（保存发生过的事，而不只是当前状态）、CQRS、DDD。
- 第 7 讲小标题：“尊重自己的小脑袋”“好的架构设计的是一片解空间”，以及 UNIX、关系数据库、Internet 三个经典案例。

## 第 8 讲 Agent Native 开发 🟢 ★★

- “Let it fail”：允许原型暴露我们的错误，才知道下一步该改实现、改规格还是改架构。
- **Ralph Loop**：`while true; do cat PROMPT.md | claude -p; done`。提示词没变，工作区变了。循环本身没有魔法，不会自己识别“完成”或“无法改进”，必须另外定义验收条件、预算和停止条件。
- **工作区是状态，agent 是状态迁移。** 长任务不能靠一段越来越长的聊天记录维持；下一轮必须能从留下的材料里判断：目标是什么、做了什么、哪些结论有证据、哪里没做完。
- 标本：两种交接。“选课功能已完成”是含糊的；“普通选课已通过，两个请求竞争最后一个名额的测试失败，失败记录在某份日志”才是能接着干的起点。**文档承担的是协作状态，不是工作量展示。**
- **重新发现 CI/CD**：“开发者是不可信的”，人也一样。把“好”变成具体条件，每次集成都检查。有检查和检查有约束力是两回事：测试失败还能照常合并，那只是旁边亮了一盏红灯。
- 验收流程要看失败路径：故意引入一次错误，确认门真的关得住。
- **CI 阻止，agent 修正**。把可以机械判断的偏好变成检查（文档别膨胀、模块边界别被绕过）。检查要说明为什么失败、怎么修，只给一个红叉会让 agent 猜规则。
- 边界：负责实现的 agent 不能因为过不了检查就把标准调低。**“删掉失败断言得到的绿色，与修复程序得到的绿色，颜色相同，含义完全不同。”**
- **Agent Native 四问**：人脑里的知识外部化了吗；agent 能自己看到程序行为吗；架构品味能变成可检查的规则吗；清理工作在持续发生吗。
- 三个把反馈做实的案例：Stripe（每次都必须执行的步骤写进流程，不交给模型决定；限制重试轮数）；Anthropic 的 C 编译器（16 个 agent 撞在同一个错上，改善验证方式之后任务才变得可分——“加 agent 之前先改善任务表示和反馈”）；StrongDM（把验收场景放在代码库之外，防止 agent 改测试迁就实现）。
- 清理解决不了的问题：系统建在一个已经失效的设计假设上，代码整理得再漂亮也没用。
- 实践机会会变成判断力的差距：工程判断来自比较，不做很多次、不见过很多真实系统，就很难做好。

## 第 9 讲 DeepSeek Harness 🟡 ★

- 150 行的 agent 完全可以工作，但它悄悄假设了每次请求都能顺利结束。网络一断就全断。
- **“没有收到成功消息，不等于操作没有执行。”** 文件已经移动但结果没记下来，恢复时重放就会出错。引出幂等性。
- 一个小循环被真实世界包围：暂停、取消、恢复各意味着什么；预算到了怎么办；权限不能只写进提示词；网页里出现的命令只是待处理的资料，不能自己变成用户授权。
- 本质复杂性和附带复杂性：前者来自我们对产品行为的要求，后者是实现方式额外制造的麻烦。
- **架构是用一部分自由换一类便利**。例子：进程、托管语言、LAMP、事件溯源、MapReduce。假设变了，被隐藏的细节就重新冒出来。
- dsh 的设计：Everything is a plugin；`Session = list[Event]`，同一份事实有不同的投影（模型看到的消息、界面、业务状态）。字幕补充（L09 `39:12`、`48:23–51:00`）：课堂口头把“一切皆插件、彼此解耦并互相组合”直接类比到 Actor Model（呼应 CS329Z L01 的 1973 ACTOR 谱系），并现场追问了用户中途插话的精确时机权衡——应该等当前整轮工具调用跑完再 inject，还是在下一轮模型 response 后立即注入。
- 给 agent 输入的三种语义：后续输入（排队并唤醒）、注入（补充上下文但不唤醒）、引导（让正在进行的工作尽快转向）。
- 插件组合的风险：十个上下文压缩插件各压一半，合起来剩 1/1024。局部合理不保证整体合理。
- 把 harness 接进已有应用的三件事：锁定对象、序列化对象、界面。

## 第 10 讲 软件的演化 🟢

- 用 **AI trajectory**（人与 AI 协作的过程轨迹）展示能力：怎样提问、怎样拆解、何时不接受模型的回答、拿什么证据纠正它、第二次遇到同类问题是否做得更好。
- 架构要经得起时间，而不是提前猜中一切。每个提前设计的扩展点都暗含一个预测。
- 从 dsh 的提交历史学工程：设计理由怎样留下来（RFC、ADR、Agent Notes）；工作怎样划分（原子提交、一个 PR 一个 worktree）；验收怎样分层；经验怎样进入下一轮（事故 → 复盘 → 回归测试 → 更新 skill）。
- **把“不好”挡在项目之外**：找出不好代码的特征，变成检查条件，失败就修正或重新采样。
- **标本：“番茄炒蛋（不放蒜版）”**。用户纠正“不要放蒜”，模型把这次纠正变成了标题里最显眼的内容；再纠正几次，标题变成一长串“不放”。每条要求都被遵守了，成品越来越怪。表达“坏”比表达“好”容易。
- 一直在错误的表达方式里打转时，需要**设计空间的跳跃**：重新想读者要做什么决定，而不是继续给原方案加补丁。
- 标本：老师想让模型学会自己回邮件的风格，不断加规则，至今没收敛。规则越来越多不等于模型越来越理解这个人。

## 第 11–12 讲 软件质量保障 🟡（只看了小标题）

- “任何程序员都有幻觉”“在我机器上能跑到底说明了什么”。差分测试（让两个实现互相找茬）、模糊测试。
- 从运行程序到证明程序：“一个不变式，抵过无数次运行”。证明助手是“铁面无私的反馈”。

## 第 13 讲 软件分析工具 🟡 ★★（2026-11-25 补读课件文字）

- **递归式自我改进与工具制造**：人心的意图（intent）、写下的规格（spec）与最终实现（impl）天然存在距离，传统软件工程靠版本管理、编译器、调试器等工具推进“人类 RSI”（递归式自我改进，Recursive Self-Improvement）。AI 时代可以把任务中写出的检索脚本、失败复现器和实验工具留作下次基础设施，关键问题是“它能否把这一次摸索，变成以后不必重复摸索的工具”（第 13 讲《用软件改进制造软件的方法》）。传统工具围绕语法或形式语义工作，而“这段代码符合人的真实目的么”（第 13 讲《用软件改进制造软件的方法》）过去通常仍要人回答。
- **程序作为数学对象与 Rice 定理的边界**：执行规则确定使程序可作数学对象研究，测试依赖判据（oracle）判断对错。但 Rice 定理表明，对一般程序不存在总能终止又能正确判定任意给定非平凡语义性质的万能算法——哪怕只是枚举正整数四元组检查 `n > 2 and a**n + b**n == c**n` 并在满足时中止，“它永远不会执行 abort”（第 13 讲《把程序作为数学对象》）就对应费马大定理。工程上的回答是做取舍：限制程序、性质或输入，允许回答 unknown，或接受一定误报与漏报。
- **各类分析与测试工具的取舍框架**：不同工具保留不同信息也各有盲区——类型系统在运行前拦住类型不匹配却不表达业务时序；代码检查器（Linter）把约定机械化但不保证业务正确；抽象解释用区间等近似换取健全性，代价是可能误报；单元测试守住选定案例防回归；模糊测试（Fuzzing）配合运行时检测工具（Sanitizer）寻找崩溃与越界，产出可反复运行的触发输入；基于性质的测试（Property-based testing）测一般性质并能缩小反例输入；差分测试对比多实现、蜕变测试查输入变换后的输出关系；模型检验、符号执行与定理证明在各自的模型、路径和规格假设下提供更强证据。课件给出两句核心追问：“看到绿色对勾，我们应该问：它究竟买到了什么？看到红色告警，我们应该问：它究竟留下了什么？”（第 13 讲《每一种工具保留了什么，又忘掉了什么》）
- **程序作为概率分布采样与非形式化验证**：代码同时是形式化执行对象和人类活动留下的样本，携带上下文线索。标本：两段匿名条件 `not x.foo(c1) and x.bar >= c2` 与 `x.foo(c1) and x.bar <= c2` 无法判断正误，恢复名字成 `can_watch_huang_guo_tv(visitor)` 与 `'China'`、`18` 后，就接回人的世界并暴露出地区与年龄方向该去核对什么（名字提供线索但不自动成为需求权威来源）。把形式化执行轨迹（execution trace）“翻译回人类世界”（第 13 讲《把程序作为概率分布的采样》）对照意图和规格称为非形式化验证（informal verification），其价值在于把“我觉得不对”变成具体输入和执行证据，而不是笼统夸一句“代码质量不错”（第 13 讲《把程序作为概率分布的采样》）。（讲义注明此处“验证”是希望完成的任务，大语言模型（LLM）判断不具有数学证明保证；该方向能否仅靠现有手段充分落地，课件没说清。）
- **策略交给模型，机制仍然关键**：课堂口号为“Heuristics is dead, Policy is Heuristics, LLM is Policy, Mechanism is King.”（第 13 讲《策略交给模型，机制仍然关键》），即部分启发式方法（Heuristics）与决定查哪里、如何理解结果的策略（Policy）交给模型，底层工具必须提供可靠的观察、执行、控制和重放等机制（Mechanism）。由此引出两项设想：从轨迹恢复面向人类理解的非形式化语义（informal semantics），尝试解释“这个用户请求为什么没有得到应有的处理”（第 13 讲《策略交给模型，机制仍然关键》）（讲义标注为探索方向，日志充分性、上下文完整性和解释核验问题尚待解决）；按任务动态组织软件视图，“no doc”（第 13 讲《策略交给模型，机制仍然关键》）意味着能从代码提取的结构按需解释，长期文档只需记录代码提取不出的历史选择与约束来源。
- **未来工具与架构演练**：软件生成有语法正确、语义正确、阅读自然三个不同目标；补丁让当前测试通过却可能增加耦合，单次修复成功和持续演化能力是两回事。设想之一是让 Agent 在隔离分支演练合理的需求变更，观察波及哪些模块、打破哪些假设、重做哪些验证，把“这里以后恐怕难改”（第 13 讲《软件工程工具的未来》）变成可讨论的证据。
- 对我们：单元 12（可靠性与评估）可直接拿“绿色对勾买到了什么、红色告警留下了什么”和工具取舍框架讲测试边界与判据，并用 `can_watch_huang_guo_tv` 标本讲非形式化验证；单元 16（给 agent 搭环境）用“策略交给模型，机制仍然关键”与隔离分支变更演练讲环境与可演化性；单元 17（审查、演化与交付）用“no doc”只留历史决策原因补强文档与代码审查；抽象解释、模型检验、符号执行和定理证明等形式化细节则后置不展开。

## 第 14 讲 软件发布与运维 🟡 ★（2026-11-25 补读课件文字）

- **谁来验收 AI 做成的事，以及提示词从哪来**：2026 年 11 月 Levent Alpöge 公布与 Claude 合作完成的黎曼猜想证明（涉及复平面零点实部等于 1/2），另有二人合作的三维 Navier–Stokes 方程反例（复核数值条件所需证书和计算仍待公开）及 Anthropic 署名 Claude 的 VP ≠ VNP 论文（不可误转述成 P ≠ NP）。Lean 与 Mathlib 社区的验收分两层：数论专家核对形式化命题与目标问题一致，多个独立检查器从源码重新验证推理。Alpöge 被称为“Prompt 大师”（第 14 讲《谁来判断 AI 把事情做成了？》），靠的是先在简化问题发现两种方法配合、再认出大问题同构处把 Claude 带过去，这“很难从一句通用的‘请深度思考’里搜出来”（第 14 讲《谁来判断 AI 把事情做成了？》）。此外欧拉素数倒数之和发散（`1 + 1/2 + ⋯ + 1/N ≤ ∏ₚ (1 − 1/p)⁻¹`）与“Galois 若有 LLM”说明工具让解题变便宜后人可以追问更深的问题；Lab3 递归式自我改进重测旧题防退步让老师判断品味和少样本学习（few-shot learning）不是模型的根本障碍（但提示拿实验结果对照）。
- **分发产物与发布需求照出架构决定**：本机编出 `cs-go` 发群里却报缺 `libSDL2-2.0.so.0`，因为缺少动态库加载条件；历史上如 Windows 3.0a 用 15 张 360 KB 软盘覆盖 8086/8088、286、386 三种启动模式，如今 Codex 打出 `rust-v0.173.0-alpha.4` 标签后靠持续集成与持续交付（CI/CD）为多系统多架构构建、打包、签名、验证，单次发布页列了 196 个文件（第 14 讲《把游戏发给室友》）。若临时要求手机端“点屏幕开火”，键盘事件里顺手耦合了命中、计分和存档就会改不动——“发布时才提出来的需求，考的可能是写第一条 prompt 时做的架构决定。”（第 14 讲《把游戏发给室友》）
- **从 localhost 到线上共享与真环境验收**：发 `localhost` 给室友只会访问他自己的电脑；LAMP、容器或 Serverless 能接手进程和资源分配，但“成绩存在哪里、哪个玩家有权改哪条记录，仍得由设计者回答”（第 14 讲《把 localhost 发给群友以后》）。GPT Store 选课助手设想说明从“能回答”（第 14 讲《把 localhost 发给群友以后》）查学分到“能办事”（第 14 讲《把 localhost 发给群友以后》）真选课之间隔着接口、授权与回执。南大图书馆网站证书在有效期内却不被浏览器认可，说明排查要沿着中间证书与根证书信任链找故障端证据；听到“部署好了”（第 14 讲《把 localhost 发给群友以后》）后，应切移动网络用无开发工具的机器按真实使用路径并测升级读旧档。
- **不停机更新与中间状态组合**：以南京大学苏州校区给教务系统加“校区”字段为例，若约定“选课期间全天可用”（第 14 讲《教务系统不能停，校区字段怎么加？》）而不能停机，必须按三步迁移：先加允许为空的字段让新旧程序共用库并分批补历史数据（暂标“校区待确认”（第 14 讲《教务系统不能停，校区字段怎么加？》））；等所有读端都认识新字段后再开放写端；等旧写入退场、补完最后一批后再加 `NOT NULL`。“测试如果只试‘全旧’和‘全新’两个端点，偏偏会漏掉上线现场真正运行过的组合。”（第 14 讲《教务系统不能停，校区字段怎么加？》）若用事件溯源（Event Sourcing）重放事件建新版课表，必须防止重放“地点变更”时顺手重发全班通知。
- **高并发配置陷阱与站点可靠性工程**：源码之外的配置和连接时机决定真实可用性。Nginx 混合负载实验里，热门 4 MB 文件虽在内存缓存却因工作进程被前一笔读盘阻塞平均等待 7.42 秒，开启 `aio threads` 后平均响应降到约 226 毫秒；Amazon 某远程调用设约 20 毫秒超时，新机器接流量时把首次建安全连接算入计时而超时，改为接流量前先建连接（第 14 讲《升级成功了，选课一开始又崩了》）。Google 由此发展出站点可靠性工程（Site Reliability Engineering，SRE）：从用户视角量可靠性（如选课提交约定时间内成功且刷新课表可见），用灰度发布观察“提示成功、课表里却没有”（第 14 讲《升级成功了，选课一开始又崩了》）等指标，告警不能只写“服务器异常”（第 14 讲《升级成功了，选课一开始又崩了》），要给值班工程师（on-call）定位版本与演练过的回退办法。
- 对我们：单元 12（可靠性与评估）可用 Lean/Mathlib 的“检查器验推理、领域人验命题”分工讲评测可信度，用“漏掉新旧并存中间状态”“按真实用户路径与非开发机验收”设计评估用例；单元 15、16（说清楚要什么与搭环境）可用“发布时暴露第一条 prompt 的架构耦合”和“能回答到能办事的系统集成缺口”做“判”题。涉及动态库、证书链细节、数据库不停机迁移、Nginx 线程池与 SRE 运维部分因偏重系统与运维基础，在本课后置不展开。

## 实验

- **实验 1：会成长的个人助手**。个人资料库（推荐 Markdown 加目录）、邮箱、办事大厅、手机联动、能力组合。要求把成功流程和你的纠正存成可读可改的脚本、技能或记忆。办事要保守：“万一 agent 把你的课都退了，你就完蛋了。”
- **实验 2：算力换智力**。加一个 effort 选项。把解题建模成搜索：求解 → 检查 → 根据反馈修改，预算用完或验收通过就停，新一轮没改善就保留旧的。评估要提前定标准，避免看到结果后再挑有利的指标。
- 实验 1 的设计意图写得很坦白：直接把这些需求丢给 agent，大概率得到一团 slop，每次修改都很贵，从而逼你思考怎么重新组织项目。

## 实验 3 蒸馏你自己 🟢 ★（2026-11-25 补读课件文字）

- **背景与核心目标**：自制个人助手常常“给你惊喜，但是又经常会给你惊吓”（实验 3《1. 背景》），需要反复纠正口癖，且模型或外围程序（Harness）升级后可能“一夜回到解放前”（实验 3《1. 背景》）。实验要求把平时收集的代理轨迹（Agent Trajectory）与你纠正它的对话作为“反馈训练数据”（实验 3《1. 背景》），实现系统化的提示词优化与自动“评估-改进”闭环，持续提升模型与“你”输出对齐的程度；使用更强基础模型效果显著更好，但无论什么模型都能取得正向效果（实验中未给出具体量化幅度，课件没说清）。
- **持续增长的基准评测集与两类数据**：推荐用文本或 Markdown 文件在文件系统维护自己的基准评测集（benchmark），包含两类来源：自己亲手完成的文稿或答案；以及历史纠错聊天记录，把模型的错误决策列为扣分项（实验 3《2.1 持续增长的评测集》）。目标不能设成“完全对齐”（实验 3《2.1 持续增长的评测集》），因为同一人在不同时间写同一任务结果也会不同，而应考察“能否得到正确的观点”（实验 3《2.1 持续增长的评测集》）与一致的思维方式；整理纠错数据时要小心其中包含未交代清楚的限定上下文，避免把局部纠正过度夸张成通用规则。
- **“蒸馏你自己”的闭环流程**：让 Agent 在看不到人类参考输出的隔离上下文下完成任务 → 比对 Agent 输出与人类输出的主要差异 → 修改提示词并重跑对比是否改进，循环迭代至对齐（实验 3《2.2 蒸馏你自己》）。可接入实验 2 的深度研究代理（Deep Research Agent），通过联网搜索和持续多样性采样打破固有思维。
- **典型失败模式**：第一，只看到表象看不到本质，例如读专业论文时从已知知识边界切入、提炼具体场景与动机，需要引导模型在长思维链中找到切入点，而非简单一条提示词就能做到；第二，提示词污染上下文导致过拟合（overfitting）——被“骂过”（实验 3《2.2 蒸馏你自己》）之后，Agent 或长期记忆（memory）把某些词语或工作方式设为全局禁止，反而伤害真正需要使用它们的正常场景。
- **对齐评价的设计要点**：不能直接判定“输出是否和人类一致”（实验 3《2.2 蒸馏你自己》），更不能极端到算最长公共子序列（longest common subsequence）；更合理的指标是“是否在有允许一定宽松篇幅的情况下，覆盖了原先的主要观点”（实验 3《2.2 蒸馏你自己》），并拆分成行文、断句、措辞、对读者知识的假设等明确维度，让改进更有抓手。
- 对我们：单元 7（记忆与 Skills）可直接用实验里“把限定上下文的纠正过度夸张成通用规则”和“被骂过之后过度禁止导致过拟合”作为“变坏的笔记”的典型标本；单元 12（可靠性与评估）可直接拿“持续增长的 Markdown 评测集”“为什么不用最长公共子序列而用宽松篇幅下的主要观点覆盖与多维度打分”来教评估设计；单元 21（放手与把关）对应利用协作轨迹（Agent Trajectory）沉淀反馈，至于实验里的自动化提示词优化搜索本身在总表中属于后置内容，放在单元 18（数据与微调）讲。
